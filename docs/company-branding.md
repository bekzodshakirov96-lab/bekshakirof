# Company visual identity

Company owners configure **Firma sozlamalari → Nom, logotip va rang**. The display name, subtitle, logo and primary color are shared by that company's authenticated staff. This is the business workspace's visual identity; the SaaS operator console and registered company identifier/name are independent.

Default reads return the existing BiznesControl identity and CSS palette without creating settings. A selected color derives light/dark backgrounds, navigation and readable button text; financial success/error/warning colors retain their meaning. Custom properties and the document title exist only while the authenticated company shell is mounted, and are restored on logout/unmount. Draft preview is local until explicitly saved; switching settings tabs retains unsaved drafts.

Owners may independently choose an exact background for light and dark modes under **Sayt foni**, with a picker or HEX value. Null means the previous automatic background. The selected mode's override changes the page background independently of the primary button color. Text and nearby surfaces adapt to preserve readability even for black in light mode or white in dark mode; financial colors are untouched. Preview switches to the edited mode, and changes apply to the company only on explicit save. Stored revisions without background fields read as automatic without writes or a schema migration. Older clients omitting new fields preserve saved background choices; explicit null resets only the requested mode. Both choices are included in branding audit history and tenant-isolation checks.

`companyBranding.get` requires authentication; `save` requires the company owner. Client-supplied tenant IDs, foreign logo URLs, arbitrary CSS and unknown fields are refused. The server-verified database scope and the existing tenant-scoped `app_settings` key enforce isolation. Independent `company-brand.*` revisions leave dated column/module preferences untouched. Writes serialize on the owner's row and branding head, require the expected revision, and audit before/after display fields in the same transaction. Stale saves fail before creating an image. Financial records, balances, Kassa/Fast KEG procedures and schema are unchanged.

PNG/JPEG/WebP source images up to 5 MB are normalized by the browser to a static PNG with a maximum 256px side. The server bounds base64/binary size, validates PNG structure, CRCs, dimensions, compression and decompressed scanline bounds; it refuses SVG/HTML, animation and appended payloads. It creates an exclusive random filename below the runtime's existing tenant uploads root. The existing authenticated uploads route serves images. No filename or URL is accepted from the client. A failed save removes only its newly-created file; removing/replacing a saved logo retains earlier images for audit history. Filesystem and database commits are not a distributed transaction, so a process crash can leave an unreferenced new file; historical files must not be mass-deleted as cleanup.

New firms may set their identity before choosing an activity template. Eligibility ignores only exact branding settings and branding audit rows; existing financial records, other settings/history or extra users still block a starting template. Applying a template preserves the separate identity. The two writers use the same owner-first locking order.

Validation uses disposable localhost tenants with real SQL and isolated files: independent same-key settings, owner authorization, tenant spoofing/foreign-owner refusal, parallel saves, rollback/file cleanup, retained old images and financial table fingerprints. A regression reproduces and fixes the branding-before-template conflict. Color tests cover black/white/saturated accents and readable text in both themes. A real localhost owner session exercised image selection, preview, save, reload, dark/light, draft tab switching and logout cleanup. No production database, upload directory or deployment is touched by this local feature work.
